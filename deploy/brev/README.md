# Brev OliveTin Launcher

This folder contains a Brev-specific launcher for the Multi-Agent Intelligent
Warehouse blueprint. It uses OliveTin as a small operator dashboard for known
Brev machine assumptions: 4x H100 GPUs, local NIM, persistent data under
`/ephemeral/maiw`, and a single NVIDIA API key used for both app services and
`nvcr.io` image pulls.

## Layout

- `docker-compose.olivetin.yaml` runs the OliveTin dashboard on host port `9090`.
- `docker-compose.maiw.yaml` defines the blueprint services and local NIM stack.
- `config/config.yaml` defines OliveTin actions and dashboard layout.
- `config/entities/blueprint-links.yaml` defines links to sibling blueprint apps.
- `config/custom-webui/custom.js` loads small browser-side OliveTin UI tweaks.
- `config/custom-webui/blueprint-app-url.js` promotes blueprint app links into
  the OliveTin header and opens them in new windows.
- `config/custom-webui/themes/nvidia-dark/theme.css` contains the custom layout
  and visual treatment for the OliveTin UI.
- `scripts/` contains action implementations.
- `.env` is generated by `Configure Blueprint` and must not be committed.
- `generated/entities/pipeline-status.yaml` is generated at runtime by
  `scripts/update-pipeline-status.sh` and must not be committed.
- `generated/docker-config/` stores Docker registry login state for OliveTin.

## Editing The Dashboard

Edit `config/config.yaml` to add, rename, or reorder actions. Actions are defined
under `actions:` and placed on the dashboard under `dashboards.contents`.
Dashboard links should bind to action IDs:

```yaml
- type: link
  title: Deploy Blueprint
  action:
    bindingId: deploy-blueprint
    canExec: true
    popupOnStart: execution-dialog
```

Use `popupOnStart: execution-dialog` for actions where the operator should see
logs while the command runs. Use `stdout-most-recent-execution` with the action
ID as `title` to show the latest status/output on the dashboard.

After OliveTin config edits:

```bash
cd deploy/brev
docker compose -f docker-compose.olivetin.yaml restart olivetin
```

OliveTin live-reloads some config changes, but restarting avoids stale browser
state while developing. Custom JavaScript and CSS changes usually only need a
browser refresh because `themeCacheDisabled: true` is set in `config/config.yaml`.

## OliveTin Dashboard Architecture

The dashboard intentionally uses a small amount of generated entity data plus a
custom web UI layer. Keep these boundaries in place when editing or recreating
the launcher:

- `config/config.yaml` owns the action definitions and the dashboard component
  structure.
- `scripts/update-pipeline-status.sh` owns the current pipeline state and writes
  `/entities/pipeline-status.yaml` inside the OliveTin container.
- `config/entities/blueprint-links.yaml` owns the list of sibling app links.
- `config/custom-webui/blueprint-app-url.js` owns browser-side app-link URL
  resolution, new-window click handling, and header placement.
- `config/custom-webui/themes/nvidia-dark/theme.css` owns visual styling only.

### Pipeline Status Row

The `pipelineStatus` entity should stay as one entity record with fields for
each pipeline indicator:

```yaml
entities:
  - file: /entities/pipeline-status.yaml
    name: pipelineStatus
```

`scripts/update-pipeline-status.sh` currently writes fields such as
`configure_status`, `running_status`, `data_status`, `user_status`, matching
`*_action` and `*_display` values, and diagnostic detail/output fields. The
dashboard renders those fields as four explicit `type: display` entries in one
fieldset:

```yaml
- title: Pipeline
  type: fieldset
  entity: pipelineStatus
  contents:
    - type: display
      title: '<a class="pipeline-status-button pipeline-status-button--{{ pipelineStatus.configure_status }}" href="/actionBinding/{{ pipelineStatus.configure_action }}/argumentForm">{{ pipelineStatus.configure_display }}</a>'
```

Do not split the pipeline into one OliveTin entity record per step unless you
also redesign the dashboard layout. OliveTin creates one fieldset per entity
record for entity-backed fieldsets, so four step records become four one-button
rows. The current design keeps the row shape in `config/config.yaml` and keeps
CSS generic.

Pipeline status class names are intentionally simple:

- `pipeline-status-button--complete`
- `pipeline-status-button--starting`
- `pipeline-status-button--stopped`

CSS should not know the pipeline step count or order. It only styles the generic
status classes. Stopped buttons pulse; starting and complete buttons stay solid.
The whole Pipeline row is hidden when every rendered pipeline button is complete:

```css
.dashboard-row:has(.pipeline-status-button):not(
        :has(.pipeline-status-button:not(.pipeline-status-button--complete))
    ) {
    display: none !important;
}
```

To add, remove, or rename a pipeline step, update both
`scripts/update-pipeline-status.sh` and the `Pipeline` fieldset in
`config/config.yaml`. CSS should not need a pipeline-specific change unless a
new status value is introduced.

### Blueprint App Header Links

Blueprint app links are backed by OliveTin entities, but they are displayed in
the global header:

```yaml
entities:
  - file: /config/entities/blueprint-links.yaml
    name: blueprintLink
```

`config/entities/blueprint-links.yaml` is the source of truth:

```yaml
- title: Dashboard
  slug: dashboard
```

`config/config.yaml` includes a `Pipeline Apps` fieldset that renders one hidden
anchor per `blueprintLink` entity:

```yaml
- title: Pipeline Apps
  type: fieldset
  entity: blueprintLink
  contents:
    - type: display
      title: '<a href="#" data-blueprint-app-slug="{{ blueprintLink.slug }}" onclick="return window.maiw && window.maiw.openBlueprintApp ? window.maiw.openBlueprintApp(this) : false">{{ blueprintLink.title }}</a>'
```

The fieldset is hidden by CSS, but it must remain in the dashboard unless
`blueprint-app-url.js` is changed to read app data from somewhere else. The JS
finds those hidden anchors, deduplicates them by slug, creates visible header
links, inserts the header nav immediately after `.logo-and-title`, adds an
external-window SVG icon, and opens each link in a new browser window.

The sibling app URL is derived from the current hostname by replacing the first
hostname label prefix before the first `-` with the app slug. For example:

```text
olivetin-brev-example.brevlab.com -> dashboard-brev-example.brevlab.com
```

For `localhost` and loopback hosts, the helper returns the current origin. If
Brev changes hostnames, update `buildSiblingAppHostname()` in
`config/custom-webui/blueprint-app-url.js`.

To add another header app link, add another item to
`config/entities/blueprint-links.yaml`:

```yaml
- title: API Docs
  slug: api
```

Then refresh the browser. The hidden dashboard row and header promotion should
pick it up automatically.

### CSS Hooks

The custom theme relies on a few deliberate hooks:

- `.pipeline-status-button` marks Pipeline indicators.
- `.pipeline-status-button--complete`, `--starting`, and `--stopped` drive
  status color and animation.
- `a[data-blueprint-app-slug]` marks hidden source anchors for app links.
- `.maiw-header-apps`, `.maiw-header-app-link`, `.maiw-header-app-label`, and
  `.maiw-header-app-icon` style the promoted header links.

Prefer adding semantic classes in `config/config.yaml` or
`blueprint-app-url.js` over writing CSS that depends on OliveTin's generated DOM
depth or the number of pipeline steps.

## Modifying Blueprint Configuration

`Configure Blueprint` runs `scripts/configure-blueprint.sh`. It writes
`deploy/brev/.env`, generates Postgres/JWT secrets when missing, and logs into
`nvcr.io` with:

```bash
docker login nvcr.io -u '$oauthtoken'
```

The NVIDIA API key field is a password argument and the action uses OliveTin
`exec`, so the key is passed via process environment instead of shell command
interpolation.

Account passwords are not stored in `.env`. Use the `Reset Passwords` dashboard
action after demo data is installed. Blank password fields are ignored
so operators can update only one account at a time.

If adding more config inputs, add arguments to the `configure-blueprint` action
and update `scripts/configure-blueprint.sh`. Prefer narrow validators in the
script for secrets and `regex:` validators for non-secret IDs.

## Auto-Closing Execution Dialogs

OliveTin does not provide a built-in "close on success" flag. This folder enables
custom JavaScript with:

```yaml
enableCustomJs: true
```

`config/custom-webui/auto-close-dialog.js` listens for
`EventExecutionFinished`. It redirects from `/logs/<executionTrackingId>` back
to `/` after successful completion. Failed actions stay on the log page so the
operator can read the error.

Refresh the browser after changing custom web UI files.
